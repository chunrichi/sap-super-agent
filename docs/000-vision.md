# 000 定位与原则

> 本文是本项目的方向锚点，后续文档只依赖前面已给出的概念。原始需求见 [plan.md](plan.md)，对原方案的逐条审视见 [001-review.md](001-review.md)。

## 一句话

一个面向 SAP 研发交付的 super-agent：**需求记录在 SAP，编排在控制平面，编码在开发者身边的 VSCode，重复的文档工作由服务端 AI 主动完成。**

它参考 DeepSeek 的 super-agent 设计（"让 Agent 像一个团队同事一样持续接活"），但不复刻其实现形态：

| 维度 | DeepSeek dsh-superagent | 本项目 |
| --- | --- | --- |
| Source（触发来源） | GitHub、飞书 | SAP 内自建需求系统 |
| 主进程（编排者） | DSH 主 Session，跑在操作者机器上 | 可移植的编排核心：本地进程 / 独立服务；SAP 是需求与审批的记录系统（M3 只跑批处理 AI 与投影回写） |
| Executor（执行者） | DSH worker Session + 服务端 worktree | 开发者 VSCode 扩展（Copilot Chat 人机协作）+ 服务端 AI 批处理 |
| 工作产物 | PR、评论、飞书消息 | 需求分析、开发说明、代码/传输请求、测试文档、知识条目 |
| 人的角色 | 提需求、审 PR | 需求顾问确认分析与开发说明（IT 与业务的桥梁）、开发者在 VSCode 与 Copilot 一起开发、业务方提需求并验收 |

## 三条原则

1. **注意力最小化。** 每个人只被通知"现在必须由你做"的事：一个审批、一次开发、一次验收。健康状态不占空间，进度不打扰人。
2. **上下文原地不动。** 代码和开发上下文留在开发者机器上，通过 VSCode + Copilot Chat 人机同屏处理；可审计、可复现的结构化生成放在服务端，离线也能跑。
3. **一条需求一条线。** 一个需求（Demand）只有一个状态机、一个入口、一条审计轨迹；中间系统通过 Hook 接入，而不是各自发明一套流程。

## 设计原则（沿用并裁剪参考实现）

- **概念要少。** 只有六个领域概念：需求、阶段、任务、指派、工件、门禁。新增业务需求优先做成某个概念的属性、模板或提示词，而不是新概念。
- **AI 与人的边界写成规则，不写成愿景。** 哪些阶段不需要人、哪些门禁必须人确认、哪些任务只有在线且符合条件的开发者才能接，都进入可配置的规则与状态机。
- **明确记录系统。** SAP 是需求与业务数据的记录系统（system of record）；控制平面是执行态（任务、指派、心跳、租约）的记录系统；VSCode 是代码工作区的记录系统。三者用 ID 关联，不互相写对方的真相。
- **离线不派单，但不是停止工作。** 服务端 AI 阶段 7×24 主动推进；需要人的阶段只在人真正可用时进入可领取队列。
- **诚实状态。** "已生成"、"已确认"、"已合并"是三种不同的事实；面板和 API 不把它们混成一个"完成"。

## 非目标（v1 不做）

- 不做完全无人值守地修改 SAP 生产系统或自动传输（TR 仍由人/既有流程控制）。
- 不实现 JIRA / CHARM / Confluence / Teams 的具体集成逻辑，只定义 Hook 契约与示例适配器位。
- 不做多租户 SaaS；先服务一个团队/一个 SAP 系统。
- 不替代 Copilot、DSH 或任何模型供应商；它们是可替换的执行器与模型后端。

## 术语

核心业务概念只有 6 个：Demand、Stage、Task、Assignment、Artifact、Gate；Executor、Hook 是支撑对象；Presence、Lease、Workspace、Worktree 是运行时属性；StageRun 是 Stage 的实例。

| 术语 | 中文 | 含义 |
| --- | --- | --- |
| Demand | 需求 | 业务方提交的一项诉求；状态机与审计的根对象 |
| Stage | 阶段 | 需求流水线的一步，有输入工件、输出工件与执行方式（服务端 AI / 人工客户端） |
| StageRun | 阶段运行 | 阶段的一次实际执行，含尝试次数、事件、产物与门禁 |
| Task | 任务 | 可以指派给一个执行器的具体工作单元；由阶段产生或独立创建 |
| Assignment | 指派 | 任务与执行器的一次绑定，带租约、进度与结果 |
| Executor | 执行器 | 能接活的东西：服务端 AI 执行器，或某个在线开发者的 VSCode 客户端 |
| Artifact | 工件 | 阶段产出的版本化内容：需求分析、开发说明、代码变更、测试文档、知识条目 |
| Gate | 门禁 | 必须由人确认才能继续的审批点 |
| Hook | 钩子 | 对外部系统（JIRA/CHARM/Confluence/Teams）的扩展入口，只定义契约 |
| Presence | 在线状态 | 客户端心跳声明的可用性：online / busy / away / offline |
| Workspace | 工作区 | 开发者机器上的代码目录；任务通过仓库/目录绑定匹配到这里 |
| Worktree | 工作树 | 为单个任务在本地创建的隔离检出目录，避免打乱开发者主工作区 |

## 成功标准（v1 验收）

1. 业务方在 SAP 里提交一个需求，5 分钟内控制平面收到并生成需求分析草案。
2. 一个开发者在 VSCode 里连接后，只能看到匹配自己工作区与角色的任务；合格执行器都可领取，但同一任务同一时刻只有一个持有者。
3. 开发者离线期间不会收到人工任务；重新打开对应目录后，绑定变化 2 秒内推送待办、10 秒内可见。
4. 需求分析、开发说明、测试文档均可由服务端 AI 生成并留存版本；每次人工修改可追溯。
5. 全链路可审计：每个状态变化对应一个不可变事件，事件能还原出"谁、何时、基于什么、改了什么"。
6. 本地模式下 `npx` 一条命令启动，无需数据库与外部中间件。
