## 1. 阶段计划

### S0 骨架（本地闭环）

- **目标**：不接 SAP、不接 Copilot，证明"需求→服务端 AI→任务→客户端→工件"主链路。
- **交付**：`protocol`、`core` 状态机、`server`（SQLite + REST + WS）、`cli`（`init`/`dev`）、`ai` 的 BYOK 适配器（OpenAI 兼容 + 假 LLM）与 1 个阶段（需求分析）、`clients/vscode` 任务箱（claim/完成/工件）、**手建开发任务**（S0 验证用，替代自动生成的开发阶段）、e2e 测试。
- **验收**：`npx sap-superagent dev` 启动；浏览器或 CLI 建需求；30 秒内生成需求分析工件；VSCode 连接后领取手建开发任务并回写工件；事件时间线完整。
- **失败场景**：至少覆盖 [009](009-testing.md) 的 #1、#2、#3、#10。
- **风险**：协议先行容易过度设计。对策：只实现 003 中 S0 用到的 12 个端点，schema 留扩展位。

### S1 门禁与模板

> **状态（2026-11-05）：H1 已完成**（分支 `feat/h1-gates`）。交付：Approval 状态机 + 门禁 API（通过/驳回/撤回/超时）、`default` 3 阶段（G1/G3/G4）与 `pdo` 6 阶段（G1–G5）模板、`templateId@version` 固定、工件不可变版本/supersede/stale 传播、schema+checklist 完成判定、autonomy auto/observe、golden set 评测框架（`pnpm eval:golden`，report 确定性入库）。验证：`pnpm check`、`pnpm e2e`（审批通过/驳回/超时/stale + docs/009 #1/#2/#3/#10）、`pnpm eval:golden`。

- **目标**：让"人工确认"成为一等公民，并支持 PDO 六阶段预设。
- **交付**：Approval 状态机、阶段模板（`default` 3 阶段 / `pdo` 6 阶段，见 `templates/`）、工件版本与 supersede、退回修改、审批通知（先 Web / CLI 输出，后 Teams Hook）、**golden set 离线评测脚本**（20–30 条脱敏 PDO 需求）。
- **验收**：审批前阶段阻塞、审批后推进；退回后生成新版本而不是覆盖；模板切换不影响进行中需求；server-ai 阶段完成需通过 schema + checklist；评测报告中人工修改率与自主度阈值可判定。
- **失败场景**：至少覆盖 [009](009-testing.md) 的 #13、#14、#15。
- **模板**：默认 3 阶段 = 需求分析（G1）→ 开发实现（G3）→ 验收归档（G4）；PDO 6 阶段预设 = [005 §4](005-clients-and-ai.md) 表格，二者都是配置而非代码分支。
- **风险**：审批角色与 SAP 角色映射后置，先控制平面账号。

### S2 SAP 需求系统

- **目标**：SAP 成为真实记录系统。
- **交付**：`sap/` DDIC 表、ICF 节点 `ZSA_API` + handler `ZCL_ZSA_HTTP_HANDLER`（JSON API）、MIME 托管的 Web 页面（列表 + 详情 + 审批）、事件 outbox + 后台推送 job、`sap-adapter`（webhook 验签/幂等/ICF JSON 客户端）。
- **验收**：SAP 提交需求 5 分钟内出现在控制平面；审核结果 1 分钟内回写 SAP；断网重试不重复建单（幂等键验证）；未绑定仓库的需求正常进入通用任务箱，绑定需求按工作区派发；Web 页面经 SSO 登录可用。
- **失败场景**：至少覆盖 [009](009-testing.md) 的 #6、#7、#11、#12。
- **风险**：abap-cli 仅 basic auth（与 Web/API 的 SSO 分离）；传输请求流程。对策：为开发/CI 申请专用 basic-auth 账号或网关；ICF 节点与 MIME 均可用 abap-cli 建；传输请求由团队流程管理；不自动激活到生产。

### S3 多人在线与派发

- **目标**：支持一个团队的真实协作。
- **交付**：presence TTL、lease 续约/回收、资格与工作区匹配、同用户并发限制、任务转交、断线重连补事件、客户端"打开对应目录"绑定。
- **验收**：开发者关机/断网 60 秒内任务回池且可被他人领取；未绑定任务在通用任务箱可见，已绑定任务在打开对应目录后 ≤2s 推送、10 秒内可见；重连后看到离线期间的进展；同一任务不会双写。
- **失败场景**：[009](009-testing.md) 的 #1–#5、#8、#9、#16。
- **风险**：时区/时钟漂移、网络抖动导致误回收。对策：服务端时间为准，续约失败重试 2 次再回收。

### S4 Hook 与外部系统

- **目标**：PDO 的中间步骤有正式入口。
- **交付**：Hook 契约（事件名、payload schema、幂等键、重试/死信）、`http` 示例目标、JIRA / CHARM / Confluence / Teams 四个占位适配器（文档 + 配置样例，不实现业务逻辑）、出站队列与重放命令。
- **验收**：阶段事件可配置触发一个 HTTP 目标；失败重试可见；手工重放不重复建单；契约见 [008-hooks.md](008-hooks.md)。
- **失败场景**：[009](009-testing.md) 的 #11、#12。
- **风险**：每家企业中间系统字段不同。对策：适配器只做"映射"，不在核心加业务分支；字段映射放配置。

### S5 SAP 宿主受限模式

- **目标**：满足"数据与流程尽量不出 SAP"的诉求。
- **交付**：SAP 侧 bgRFC 批处理 job 调 AI（需求分析/测试文档等结构化阶段）、SAP 内审批直接驱动阶段推进、控制平面轻服务与 SAP 同网段部署（或内嵌于 ABAP 的 HTTP 调用）、M3 部署文档。
- **验收**：无任何开发者在线时，需求分析与测试文档仍能生成；审批在 SAP 内完成；敏感内容不离开企业边界。
- **风险**：ABAP 侧 AI 调用与长任务的管理复杂度。对策：只做"批处理 + 轮询"，不做交互式会话；失败可重试、可人工补跑。

## 2. 开源发布节奏

| 版本 | 内容 | 面向 |
| --- | --- | --- |
| `v0.1.0` | S0 + S1，本地模式一条命令跑通，含 GIF 演示与 Docker 一键启动 | 早期试用者、内部评审 |
| `v0.2.0` | S2 + 文档站（可先用 GitHub Pages），SAP abapGit 包 | SAP 团队试用 |
| `v0.3.0` | S3 + VS Code Marketplace 预览版（或 VSIX 分发） | 多开发者团队 |
| `v0.4.0` | S4 Hook 契约 + 示例 | 集成方 |
| `v1.0.0` | S5 可用、协议冻结、迁移指南、安全审计 | 企业采用 |

每个版本发布前检查：README 与 docs 的快速开始能跑通、有无破坏性变更说明、示例配置更新、CHANGELOG 生成、许可证/安全声明更新。

## 3. 给一个人 + AI Agent 的推进建议

- 每个切片按"协议 → 核心 → 宿主 → 客户端 → e2e"顺序做，Prototype 先行（可在本地用假 SAP / 假 LLM 跑）。
- 一个切片一个里程碑，一个里程碑一个 grep 得到的验收命令（见各阶段验收）。
- 文档先行但克制：实现偏离 003 时，先改文档再改代码；未实现的契约标注 `status: draft`。
- 先不做的事：UI 美化、多租户、SSO、移动端、复杂权限 DSL、ABAP 侧全量控制平面。这些都在 v1 之后按真实反馈决定。
- 衡量"更好"的唯一标准：一个需求从提交到可验收的时间是否缩短，以及人被打扰的次数是否减少。

## 4. 成功度量（上线后观察）

| 指标 | 目标 | 采集方式 |
| --- | --- | --- |
| 需求提交 → 分析草案 | ≤5 分钟（AI 阶段可用时） | 事件时间戳 |
| 需求提交 → 首次可开发 | ≤3 个工作日（先采集 PDO 近 3 个月基线后校准） | 事件时间戳对比 |
| 人工介入次数/需求 | ≤3 次（需求顾问确认分析 G1、开发评审 G3、业务验收 G4） | Approval + 人工任务计数 |
| 离线误派 / 双写 | 0 | 租约与幂等冲突日志 |
| 每个需求的 AI 成本 | 可配置上限，按阶段统计 | run ledger |
| 开发者满意度 | 主观评分 ≥4/5 | 季度问卷 |
