# 004 SAP 侧设计

本文定义 SAP 内需求系统的对象、接口与开发方式，以及"主进程放在 SAP"的可行边界。控制平面协议见 [003-domain-and-protocol.md](003-domain-and-protocol.md)。

> 目标系统：**S/4HANA（HANA）**。SAP 侧走 **ICF + MIME** 路线：一个 ICF 节点同时提供 JSON API 与 MIME 托管的 Web 页面，不引入 RAP/OData/Fiori Elements。认证走 SSO；v1 暂不建模细粒度权限。

## 1. 边界：什么放 SAP，什么不放

SAP 是企业内权限、审计、审批与数据合规的天然载体，但不是 agent 运行时。建议按"记录系统 / 执行态"切分：

| 放在 SAP | 不放在 SAP |
| --- | --- |
| 需求主数据、业务字段、附件 | 任务租约、心跳、presence |
| 审批记录与审批角色 | 阶段执行的运行时状态机（ABAP 可做批处理驱动，但状态仍建议由控制平面持有） |
| 工件的元数据与审计 | 大模型会话、prompt、token 记账 |
| 对外事件 outbox 与推送日志 | VSCode 客户端注册与设备信息 |
| 面向业务方的 SAP 内 Web（ICF + MIME） | 控制平面的 Web 详情页与队列管理 |

原则：**SAP 存业务事实，控制平面存执行事实，两边用 ID 关联**。SAP 不主动修改执行态字段；控制平面通过受限服务账号只写"状态投影"与工件元数据。

## 2. 数据模型（DDIC，本地包 `$ZSA`）

> **包决策（2026-11-05，用户）**：Phase B 用本地包 `$ZSA`（`$` 前缀本地包，对象仅在测试系统生效，不需要传输请求）；全部对象用 abap-cli 创建/推送/激活。abapGit 本轮不实现。
>
> **Phase B 实测（2026-11-05，测试系统）**：`$ZSA` 实测不存在，已用 `abap create DEVC '$ZSA' --package '$TMP' --package-type development --yes` 创建（super=`$TMP`、swcomp=LOCAL），存在性以 `abap select TDEVC` 为准（`abap list --package` 对不存在的包也返回 success/count=0，是假阴性）。
> DDIC 表由一次性 bootstrap 程序 `ZSA_DDIC_BOOTSTRAP` 创建（`abap create TABL` 在 abap-cli 2.2.0 上无法建含数值/深类型字段的表，见 [sap/README.md](../sap/README.md) 与上游 issue chunrichi/abap-cli#34）；表结构与 `sap/src/*.tabl.*` 逐字节 round-trip 一致。
> 实现约束（真机）：`COMMENT` 是 DDIC 保留字 → `ZSA_APPROVAL` 列名 `DECISION_COMMENT`（对外 JSON 字段名仍 `comment`）；`STRING` 列不能 `NOT NULL`（`ZSA_EVENT_OUT.PAYLOAD`）；含数值/深类型的表实际增强类别为 EXCLASS 3/4。

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `ZSA_DEMAND` | `MANDT`, `DEMAND_ID`(CHAR32), `DEMAND_NO`(CHAR12), `TITLE`, `REQ_USER`, `ORG_UNIT`, `PRIORITY`, `TEMPLATE_ID`, `TEMPLATE_VERSION`(NUMC4), `REPO_KEY`(CHAR64), `PROJECT_KEY`(CHAR40), `STATUS`, `STATUS_TEXT`, `STAGE_KEY`, `VERSION`(INT4), `CREATED_AT`, `CHANGED_AT`, `SAP_NOTE` | 需求主表；`STATUS` 是面向业务的投影（见 2.1）；`REPO_KEY`/`PROJECT_KEY` **可空**：需求不强绑仓库；需要时由需求顾问补充，或由用户账号维护的工作区映射决定派发范围 |
| `ZSA_DEMAND_T` | `DEMAND_ID`, `LANG`, `DESCRIPTION`(STRING), `ACCEPTANCE`(STRING) | 长文本与验收标准 |
| `ZSA_ARTIFACT` | `ARTIFACT_ID`, `DEMAND_ID`, `STAGE_KEY`(CHAR30), `STAGE_RUN_ID`(CHAR32), `KIND`, `VERSION`, `CHECKSUM`, `CONTENT_REF`, `CONTENT_TYPE`, `STATUS`, `AUTHOR_TYPE`, `AUTHOR_ID`, `CREATED_AT` | 工件元数据；按阶段分组展示；模型/prompt 版本留在控制平面，不回写 SAP |
| `ZSA_APPROVAL` | `APPROVAL_ID`, `DEMAND_ID`, `STAGE_KEY`, `GATE_KEY`, `STATE`, `REQUIRED_ROLE`, `DECIDED_BY`, `DECIDED_AT`, `DECISION_COMMENT` | 门禁记录（审计用）；`COMMENT` 是 DDIC 保留字，列名用 `DECISION_COMMENT`，JSON/协议字段名仍是 `comment` |
| `ZSA_EVENT_OUT` | `EVENT_ID`, `TYPE`, `DEMAND_ID`, `PAYLOAD`(STRING), `STATE`, `ATTEMPTS`, `NEXT_AT`, `CREATED_AT` | 出站事件 outbox（至少一次投递 + 幂等键） |
| `ZSA_CFG` | `CFG_KEY`, `CFG_VALUE`(STRING) | 极少量配置：控制平面地址、HMAC key 引用（不存明文密钥） |

### 2.1 状态投影

`ZSA_DEMAND-STATUS` 是**投影字段**，由控制平面通过服务接口回写，业务方在 SAP 只能看、不能改；业务方在 SAP 改的是标题、描述、验收标准、审批决策。映射表驱动、只维护一份（`sap-adapter`），避免两边各写一套：

| 控制平面 Demand / StageRun | SAP `STATUS` |
| --- | --- |
| `submitted` 且阶段未开始 | 待分析 |
| 任一 `server-ai` 阶段 running | 分析中 |
| 任一 Approval `pending` | 待确认 |
| 开发阶段 running / 等待派发 | 开发中 |
| 全部阶段完成，等待最终验收 | 待验收 |
| `done` | 已完成 |
| `cancelled` / `rejected` | 已取消 / 已驳回 |

### 2.2 ID 与幂等

- `DEMAND_ID` 用 `cl_system_uuid=>create_uuid_c32_static( )`；它**就是**协议里的 `demandId`，控制平面不二次生成；`DEMAND_NO` 用号段对象（`ZSA_DEMAND` number range），给人看。
- 事件 outbox 的 `EVENT_ID` 即幂等键；控制平面按它去重，重投不产生副作用。
- 所有时间字段用 UTC（`TIMESTAMPL`）。
- `ZSA_DEMAND-VERSION` 是控制平面回写的乐观并发版本（初始 1，每次 PATCH/审批自增）。控制平面
  用 `If-Match: <VERSION>` 写回；版本不一致返回 `409` + `currentVersion`，控制平面重拉后重放
  （docs/009 #12）。它只是回写通道的并发控制字段，不是业务状态。

## 3. 服务接口（ICF JSON API）

### 3.1 三条通道

| 通道 | 方向 | 方式 | 用途 |
| --- | --- | --- | --- |
| 入站事件 | SAP → 控制平面 | outbox + 后台 job → HTTPS POST `/hooks/sap`（HMAC） | 需求提交、字段变更、审批结果、取消 |
| 回写 | 控制平面 → SAP | HTTPS JSON（ICF 端点，服务账号 + TLS） | 状态投影、工件元数据、审批同步 |
| 拉取对账 | 控制平面 → SAP | HTTPS JSON 增量查询（`CHANGED_AT` 游标） | 断点补漏、事件丢失兜底 |

先实现"入站事件 + 回写"，对账 job 作为 S2 验收项。

### 3.2 ICF 服务与 JSON API

- 一个 ICF 节点 `/sap/zsa`（SICF 节点名 `ZSA`；AFF 文件 `sap/src/zsa.http.json`），handler 类 `ZCL_ZSA_HTTP_HANDLER` 实现 `IF_HTTP_EXTENSION`，同一入口服务两类请求：
  - `/sap/zsa/api/*` → JSON 业务接口；
  - `/sap/zsa/ui/*` → 从 MIME Repository 读取静态前端资源（`cl_mime_repository_api`）。
- JSON：UTF-8、`application/json`；统一错误信封 `{"error":{"code":"...","message":"..."}}`；S/4HANA 可用 `xco_cp_json`，兼容层用 `cl_sxml_string_writer`/`/ui2/cl_json`。
- 最小路由集：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/demands` | 列表；`?status=&changedSince=&q=` |
| GET | `/api/demands/{id}` | 详情 + 工件 + 审批 + 事件时间线 |
| POST | `/api/demands` | 创建需求（Web 页面用） |
| PATCH | `/api/demands/{id}` | 控制平面回写：状态投影/工件元数据（只允许约定字段）；必须带 `If-Match: <VERSION>`，不匹配返回 `409` |
| POST | `/api/demands/{id}/approvals` | 审批决策 |
| GET | `/api/health` | 运维探活 |

- handler 内做输入校验与字段白名单；回写只接受 `STATUS/STATUS_TEXT/STAGE_KEY` 与工件元数据，业务字段由 Web 页面维护。
- 控制平面使用服务账号 `ZSA_CP_SERVICE` 调接口（TLS + OAuth2 client credentials 或专用服务账号 basic over TLS），不复用终端用户。
- 认证：Web 页面走 ICF 登录（SSO，见 §5）；API 服务账号独立。
- 回写只允许 `STATUS / STATUS_TEXT / STAGE_KEY / ARTIFACTS / APPROVAL`（`ZCL_ZSA_HTTP_HANDLER=>is_writeback_field_allowed`）；
  `TITLE / DESCRIPTION / ACCEPTANCE / REQ_USER / REPO_KEY / PROJECT_KEY` 等业务字段一律拒写，由 SAP Web 维护。
- 响应里的 `version` 即 `ZSA_DEMAND-VERSION`，控制平面把它作为下一次 `If-Match`。

### 3.3 出站推送 job

- 类 `ZCL_ZSA_EVENT_PUSH`：选中 `STATE='NEW'` 的 outbox 行，`cl_http_client=>create_by_url` POST，带 `X-SA-Signature`、`X-SA-Timestamp`、`X-SA-Delivery`。
- 成功置 `SENT`；失败按 1s/5s/30s/5min/30min 退避，超过 24h 置 `DEAD` 并在监控报表暴露。
- 调度：`bgRFC`（推荐，可靠）或每 1 分钟的后台 job（最低成本）。ECCP 无 bgRFC 时用 job。
- HMAC 密钥通过 SAP secure store（`SSF`/`CL_ABAP_SEC` 或环境变量注入）读取，不落表明文字段。

**报文与签名（与 `packages/sap-adapter` 的实现必须一致）**

```http
POST <ZSA_CFG-CONTROL_PLANE_URL>/hooks/sap
Content-Type: application/json
X-SA-Signature: sha256=<hex(HMAC-SHA256(secret, rawBody))>
X-SA-Timestamp: 2026-11-05T08:00:00.000Z      # UTC ISO-8601；控制平面也接受 epoch 秒/毫秒
X-SA-Delivery:  <ZSA_EVENT_OUT-EVENT_ID>       # 幂等键，重投保持不变

{"eventId":"<EVENT_ID>","occurredAt":"2026-11-05T08:00:00.000Z",
 "data":{"type":"demand.submitted","demand":{ "demandId":"...", "...": "..." }}}
```

- `data.type` ∈ `demand.submitted` / `demand.updated` / `artifact.approved` / `artifact.rejected` /
  `demand.cancelled` / `hook.receipt`（语义见 docs/003 §4.5）。
- 控制平面在 ±5 分钟窗口内校验时间戳（`SA_SAP_HOOK_TOLERANCE_MS` 可调），签名或窗口失败返回 `401`；
  同一 `X-SA-Delivery` 重投返回 `200 {duplicate:true}` 且不产生副作用（docs/009 #11）。
- `body.eventId` 若出现必须等于 `X-SA-Delivery`，否则 `400`。
- 控制平面回写同样按"可重试/永久失败"分类：网络/超时/5xx/429 指数退避（2s 起、上限 5min、最多 5 次），
  4xx 进死信；`409` 先重拉 `GET /api/demands/{id}` 刷新 `VERSION` 再重放一次（docs/009 #12）。

### 3.4 联调与运维入口

- 控制平面入站端点：`POST /hooks/sap`；运维状态：`GET /hooks/sap/status`（admin token，输出
  `enabled.outbound/inbound` 与 outbox `pending/sent/dead/lastError`）。
- 对账命令：`pnpm sap:reconcile [--state-dir <dir>] [--changed-since <ISO>] [--limit <n>] [--json]`
  （只读，输出差异清单；exit 3 表示有差异需人工处理）。
- 离线源码校验：`pnpm sap:check`（`abap validate:aff` + `abap check content`；无 SAP 系统时跳过
  `abap check syntax` 并说明）。
- SAP 侧源文件在仓库 `sap/`（abapGit + abap-cli AFF 布局），导入顺序与 Phase B 清单见
  `sap/README.md`。

## 4. SAP 内 Web 应用（MIME 托管）

不做 Fiori Elements / RAP；前端是一组静态资源，上传到 MIME Repository，由 `/sap/zsa` 节点在 `/sap/zsa/ui/` 下提供。

页面（保持最少）：

1. **需求列表**：编号、标题、状态、负责人、更新时间；筛选状态与"我的待办"。
2. **需求详情**：描述、验收标准、工件（按阶段分组）、审批操作（通过/驳回 + 一句话意见）、事件时间线（只读）。

实现路线：

- 纯静态 SPA（原生 JS 或 SAPUI5 均可），只调用同一 ICF JSON API，不引入 OData 模型。
- MIME 目录 `/zsa/ui` 用 `abap mime push` 上传；`index.html` 作为默认页，handler 处理 `/ui/*` 时默认回落 `index.html`。
- 审批提醒：优先 SAP 内通知（worklist/邮件）；Teams/JIRA 等通过 Hook 接入。

## 5. 认证与权限

**认证（支持 SSO）**：

- Web 页面：ICF 登录流程走企业 SSO（SAML/IdP 或 SAP logon ticket）；handler 从登录上下文取当前用户，不自行校验密码。
- 服务调用：控制平面用独立服务账号（IdP 的 OAuth2 client credentials，或专用服务账号 basic over TLS）；凭据只存控制平面的 secret manager。
- 客户端不持有 SAP 凭据：VSCode 的 ABAP 操作在本地通过 `abap-cli` 的专用开发用户执行，控制平面与模型看不到凭据。

**权限（v1 暂不建模）**：

- v1 不做细粒度 SAP 授权对象/角色矩阵；Web 访问依赖 ICF 登录（SSO），操作人记录为登录用户。
- 业务角色（业务方 / 需求顾问 / 开发者）暂作为需求字段与控制平面标签，用于门禁指派与展示；后续按现场 SAP 权限体系再收紧。
- 仍需保证：回写接口字段白名单、服务账号最小权限、输入校验、审计字段（谁在何时改了什么）。
- 需求顾问不装 VSCode：受理、确认与审阅全部在 SAP 内 Web 完成，以 Approval 驱动阶段；VSCode 只承载开发类人工任务。

## 6. 用 abap-cli 开发 SAP 侧

本仓库已带 abap-cli 技能（`.agents/skills/abap-cli-*`）。SAP 侧对象按如下工作流开发：

```sh
abap doctor                                              # 环境与连接自检
abap select --table TDEVC --fields DEVCLASS --where "DEVCLASS = '\$ZSA'" --json
                                                         # 本地包存在性（abap list 有假阴性）
abap create DEVC '$ZSA' --package '$TMP' --package-type development --yes   # 首次前提
abap run-report ZSA_DDIC_BOOTSTRAP --json                # DDIC：6 张表（create TABL 缺陷绕行）
abap pull ZCL_ZSA_EVENT_PUSH --type CLAS                 # 类：先拉后改
abap push zcl_zsa_event_push.clas.abap
abap check syntax                                        # 全量或指定对象语法检查
abap activate ZSA_DEMAND --yes                           # 激活

# ICF 节点（类型码是 HTTP，不是 SICF）：先拉后改
abap create HTTP ZSA --file sap/src/zsa.http.json \
  --package '$ZSA' --yes
# MIME 前端资源（依赖 abap deploy 的自带 ICF handler）
abap mime create /zsa/ui --package '$ZSA' --yes
abap mime push sap/ui --root /zsa/ui --yes              # 若本地包仍要求 TR，先 --dry-run 确认
```

- DDIC 用 `abap-cli` 的 tabl 模板（本仓库 `.agents/skills/abap-cli-edit/assets/tabl-templates/`），先建数据元素、域、表，再建 ICF 节点与前端。
- ICF/MIME 命令依赖 `abap deploy` 部署的自带 ICF 服务；执行前先 `abap deploy status`；`mime create/delete` 非 TTY 必须带 `--yes`。
- 类/接口用 `abap create local` 或 `abap pull --type CLAS`，本地编辑后 `push` + `check` + `activate`。
- 本地包 `$ZSA` 无需传输请求；若未来切到非本地包，所有改动绑定 TR。`abap check` 不过不 `activate`。
- 自动化边界：CI 只能连测试系统做 `check` 与单测，**不自动激活到生产**；生产传输走企业既有流程（CHARM 等）。
- ABAP Unit 覆盖：outbox 选取与退避、HMAC 头、字段映射、审批状态机。

**工具前置条件（已实测/官方文档核实）**：

- 项目要求 **abap-cli ≥ 2.2.0**（本机实测 2.2.0，`abap doctor` 通过；上游已更新到 2.6.x/51 类，扩展与 CI 启动时校验版本，低于下限拒绝执行）。DDIC/数据/报表等类型需要先 `abap deploy --yes` 部署自带 ICF 服务 `/sap/abap_cli`（生产建议 `--package/--tr`）。
- `abap-cli` 需要 **Node 24.22.1+**；**只支持 basic auth**（不支持 X.509、浏览器 SSO、OAuth password grant、Kerberos）。若目标 SAP 系统强制 SSO，这是硬阻塞，需要企业网关/服务账号方案或换成 ADT 直连方案。
- 通道限制：`DDLS` 在 ECC 旧内核不支持；`SRVB`/`DEVC` 不能 push；这些对象用 GUI/abapGit 导入
- 不要真的修改生产系统；所有开发先连测试系统。

## 7. "主进程放在 SAP"的可行边界

结论先行：**SAP 可以承载"需求系统 + 审批 + 批处理式 AI 阶段 + 定时调度"，不建议在 ABAP 里实现完整的交互式 agent 主循环。** 具体依据与替代方案：

| 能力 | 放 SAP 的可行性 | 建议 |
| --- | --- | --- |
| 需求 CRUD、审批、审计 | 高（原生能力；ICF + JSON 足够，不需要 RAP） | 放 SAP |
| 阶段状态机（确定性） | 中（ABAP 可实现，但调试与演进成本高） | 优先放控制平面；SAP 只存投影 |
| 服务端 AI 生成（结构化、批处理） | 中（S/4HANA 上 ABAP AI SDK 可用性按 release/许可确认；也可走企业 AI 网关；长任务用 bgRFC） | M3 时放 SAP，作为"离线批处理执行器"；否则由控制平面 BYOK 执行 |
| 交互式多轮会话、流式输出 | 低（ABAP 运行时不匹配；无 Node 运行时，服务端 Copilot SDK 无法部署） | 不放 SAP；交给 VSCode / 独立服务 |
| WebSocket 推送执行器 | 低（APC 自 7.40 SP05 可用，但需 Basis 配置、连接数与运维成本高；客户端通常不可达） | 由客户端主动连控制平面（或短轮询 SAP） |
| 任务租约、presence 调度 | 低（高频写、低延迟要求不适合 ICF work process 模型） | 放控制平面 |
| SAP 反向推送/连接开发机 | 不可行（NAT/防火墙，且难携带用户身份） | 只做客户端→SAP 或客户端→控制平面 |

三种落地方式，推荐程度递减：

1. **SAP 记录 + 控制平面轻服务**（推荐）：SAP 做需求与审批；控制平面（M2）部署在同网段，通过 ICF JSON/HTTPS 交互。数据出 SAP 的只有需求文本与工件元数据（BYOK 自部署/有安全协议，无额外外发限制）。这是唯一能同时满足"离线不派单 + Copilot 人机协作 + 服务端 AI"的形态。
2. **SAP 记录 + SAP 批处理 AI 阶段**（M3）：SAP 内 bgRFC job 负责"需求分析/测试文档"等结构化阶段，调用 ABAP AI SDK / 企业 AI 网关；控制平面只处理人工任务与客户端派发。适合"数据不出 SAP"的强监管场景，但要接受无流式、模型能力受 SDK 约束、开发调试成本高。
3. **全 ABAP 主进程**（不推荐）：把 Router/Worker、会话运行时、工具调用全部用 ABAP 实现；ABAP 侧无 Node 生态、无服务端 Copilot SDK，APC/ICF 运维与长连接限制都会成为长期负担。

### 7.1 M3 落地边界（S5 实现口径）

S5/M3 采用"方式 2"的一个受控子集，边界如下（协议见 [003 §4.8](003-domain-and-protocol.md#48-sap-批处理-ai-执行器m3s5)）：

- **SAP 只做批处理执行器**：控制平面把 `server-ai` 阶段渲染成 job（prompt 由控制平面 `renderAiStageMessages` 生成），SAP `ZCL_ZSA_AI_BATCH` 取 job → 调企业 AI 网关（默认 OpenAI 兼容 `/chat/completions`）→ 回传模型**原始输出文本**。SAP 不拼 prompt、不做 JSON 提取/schema/checklist/门禁判断。
- **控制平面仍独占**：job 队列/租约/幂等、输出校验、attempt ledger、工件版本、门禁与审批推进、事件与审计；SAP 内审批（H2 审批联邦）继续走 `/hooks/sap`，S5 不新增 ABAP 控制逻辑。
- **默认关闭**：`SA_SAP_AI_BATCH` 未设置/`0` 时仍是控制平面 BYOK 本地执行，H0–S4 行为不变。
- **数据边界**：需求/工件/事件/日志留在企业内；prompt 与输出只在"控制平面 → SAP → 内网网关"路径传输；控制平面不持有网关 key（`ZSA_CFG` 只存 `AI_KEY_REF` 安全存储引用）。
- **部署形态**：轻量控制平面（Node + SQLite）与 SAP 同网段，SAP→控制平面（job API + `/hooks/sap`）与控制平面→SAP（ICF 回写/对账）均在内网；部署/网络/密钥/runbook 见 [010-m3-deployment.md](010-m3-deployment.md)。
- **不做**：ABAP 内交互式 agent、流式输出、暂停/恢复 UI、bgRFC 之外的调度抽象（SM36 周期 job 为默认通道，bgRFC 为 Phase B 可选）。
